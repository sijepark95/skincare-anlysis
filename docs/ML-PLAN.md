# Model development plan

Status: **offline research implemented; retail inference remains mock**. The MVP uses visibly labeled questionnaire-based mock observations. Running the application never authorizes or starts customer photo upload, AI-Hub download, model training, model download or PyTorch inference. The approved promotional hero video is not evidence of a working analysis model. The separate, explicitly invoked training tools and reproducible commands are in [../ml/README.md](../ml/README.md).

Current supplied-data findings are in [ML-DATA-AUDIT.md](ML-DATA-AUDIT.md). Its schema matches dataset 71886 rather than the originally proposed 71645. The user confirmed training and intended commercial-use permission on 2026-10-11; the private registry records that statement, not an independent review of the approval document. The active internal experiment classifies middle-region CSV pore codes NVP/VP. Label meaning/rater provenance and person grouping remain unverified, so experimental metrics cannot establish product performance. Downloaded data and weights remain outside the application.

## 1. Licensing and data registry before access

The proposed initial source is AI-Hub's [Korean skin condition measurement dataset (71645)](https://aihub.or.kr/aihubdata/data/view.do?currMenu=115&dataSetSn=71645&topMenu=100). The public description distinguishes instrument measurements from optional expert grades and region boxes; verify the actual files and codebook before choosing a prediction target.

The user is Korean and plans to operate the training PC physically in Korea. This supports planning a domestic application, but is not proof that access or commercial/deployment permissions have been granted. Confirm the actual applicant, approval, dataset-specific conditions, attribution, permitted processing location and commercial use. Obtain a written answer about overseas deployment or distribution of trained weights if intended. Do not infer that permission to access raw data also authorizes every derivative or transfer. Consult the current [AI-Hub usage policy](https://www.aihub.or.kr/intrcn/guid/usagepolicy.do?currMenu=151&topMenu=105) and the dataset provider; retain the dated agreement rather than relying on a summary of general terms.

Create a private dataset registry outside this repository and outside OneDrive/cloud sync. For each source record: owner, dataset/version, agreement and approval evidence, permitted purposes/regions, expiry or revocation conditions, attribution, raw-file checksums, label codebook and provenance. Record a separate license/provenance entry for pretrained weights and any third-party face detector. Never put data, credentials, original subject identifiers, image paths revealing identity, or model checkpoints in application Git history or public artifacts.

## 2. Audit labeled data and select one valid task

Inventory files, actual subject IDs, capture sessions, cameras, angles, image dimensions, boxes and label coverage. Check missing/corrupt files, label ranges, grades versus continuous measurements, repeated measurements, class imbalance, inter-rater information and duplicates. A missing optional field is missing data, not a zero or a healthy example. Audit a representative sample visually in the permitted environment and publish only aggregate findings.

The current research target is **categorical CSV pore-code classification on middle-region images**, preserving NVP/VP without inventing clinical meanings. The previous forehead wrinkle proposal applies only if a different approved package provides verified expert forehead labels and crops; the supplied 71886 files do not establish that target. Do not combine unrelated makeup preference, ingredient efficacy, expert grade and instrument measurement labels into one classifier.

RGB appearance is not a direct physical measurement of hydration, elasticity, skin barrier function or ingredient efficacy. Having instrument values in the training set does not establish that an ordinary retail camera can reproduce those instruments. The MVP's `dehydration` concern is a questionnaire preference and its score is mock. Do not present a future image prediction as measured skin water content without separate validated evidence, an appropriate intended use, and a reviewed product claim.

## 3. Subject-disjoint offline baseline

Run training in a separate, explicitly invoked workspace on the approved PC. Keep the web/service runtime independent. Candidate baseline: [Torchvision ConvNeXt-Tiny](https://docs.pytorch.org/vision/stable/models/convnext.html), with reviewed pretrained-weight terms and a task-specific head. Lock the Python/PyTorch/Torchvision/CUDA versions in that training workspace after checking hardware compatibility; the FastAPI mock environment does not install them.

For release-grade evaluation, generate an immutable person-separated train/validation/test manifest before tuning, with 70/10/20 as an initial planning ratio subject to class/person coverage. Group every image, angle, device capture and visit for one person into the same partition. Detect exact and near duplicates across partitions, including aliases. Keep a locked test set inaccessible to checkpoint/hyperparameter selection. The current plumbing experiment preserves the publisher splits and marks person grouping unverified. Actual byte hashing found cross-partition duplicate photos: default preparation rejects them; an explicitly selected exclusion policy removes all occurrences from both prepared partitions. This does not resolve repeated people or near duplicates and must not be described as leakage-free evaluation. Never merge publisher validation into training.

Use a frozen majority/constant or simple reference baseline, then a pretrained ConvNeXt-Tiny baseline with a briefly frozen backbone followed by controlled fine tuning. Use training-only augmentation and normalization estimates, fixed seeds, mixed precision only when supported, validation-selected early stopping and checkpoint selection. Audit augmentation for label preservation. Do not augment or balance the validation/test sets. Record actual configuration and experiments rather than promising a particular accuracy.

For ordinal grades report MAE, macro F1, class confusion and per-grade recall. Add subject-level confidence intervals; compare against the simple baseline on the same manifest. Track failure rate and subgroup sample counts, not only an overall score. Subject demographics in the source are evaluation metadata when legally permitted, not attributes the kiosk should infer or store by default.

## 4. Quality gating, uncertainty and field validation

Treat inference as a full camera-to-result pipeline: face presence, single face, pose/occlusion, crop validity, focus, exposure and required region coverage must pass before prediction. An annotation crop used during research is not a production detector. Train-only preprocessing and the actual deployed cropper must be tested end to end.

Define a versioned model output for the actual target, with explicit `accepted`, `retake` and `unavailable` states. Validate rejection thresholds on the validation split. Calibrate model confidence on a held-out calibration partition or within validation; report calibration and coverage/error tradeoffs. A softmax score is not automatically a calibrated confidence or a physical measurement. Low-quality or uncertain inputs must yield a retake/unavailable state, never an invented score or a silent mock fallback.

Before deployment, evaluate the locked test set once for the selected release and then a separate consented store-camera pilot. Cover actual tablet/mirror cameras, lighting, exposure, makeup, poses, accessories and the intended population. The proposed Korean dataset alone does not establish performance for all US retail customers, ages or skin tones. Investigate subgroup errors and uncertain/retake rates, recruit additional permitted validation data where coverage is insufficient, and avoid unsupported population claims. Approve product claims and a measurable release threshold before the pilot; thresholds must reflect observed data and intended use, not an arbitrary promised accuracy.

## 5. Controlled deployment and independent recommendations

Promote only a reviewed artifact with checksum, architecture/config, preprocessing/cropper version, data/split registry references, licenses, evaluation and calibration reports, intended use, limitations and rollback target. Implement inference in the FastAPI infrastructure adapter; application use cases depend on the provider port. Keep offline training jobs separate from serving and never trigger training from a customer session. The current questionnaire-only API must gain an explicitly reviewed, versioned ephemeral-image contract before accepting image bytes. Update consent and cleanup behavior at the same time; default to memory-only processing, no body logging, no photo storage and no third-party transmission.

Use a feature flag and a small approved pilot, with rollback to the explicitly labeled demo experience or an unavailable state chosen by the operator. Monitor aggregate latency, errors, quality rejection, uncertainty coverage and model version without images, raw answers or identifiable payloads. Customer photos are not training data by default; any future contribution needs a separate, voluntary consent and a dedicated governed collection pipeline.

Keep recommendations independent: selected skincare goals → approved versioned ingredient policy → eligible store products. Inventory, publication, full formulation, exclusions and store ownership remain hard filters. A new product does not require image-model retraining. Makeup is a separate future task with its own data/labels. An optional hosted LLM may later explain vetted structured matches using templates and product facts; it must not invent diagnoses, ingredient efficacy or safety, and receives no face photos. LightGBM/LambdaRank is a later ranking experiment only after lawful, reliable preference/outcome labels exist; do not train it on fabricated mock consultations or equate clicks/sales with skin efficacy.

Release gates: documented permission → label/task audit → subject split and duplicate audit → baseline comparison → quality/uncertainty validation → independent camera/population validation → reviewed claims/privacy/API → restricted pilot → monitored release. Until each applicable gate is met, real analysis remains unavailable.
